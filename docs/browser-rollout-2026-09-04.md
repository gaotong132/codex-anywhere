## 验收发现并修复

1. Windows 启动器未持久读取浏览器端点配置：新增 `browserEndpointFile`。
2. 切环境途中旧授权按钮仍可点：连接/切换期间禁用会话选择与授权，失败后不沿用旧连接状态。
3. MCP 写操作审批未转发：接入标准空表单及旧版专用 MCP 审批问题，只支持单次批准/拒绝。
   其他表单、缺少身份、不同任务和过期轮次不变成泛化审批；不写入永久批准配置。
4. CLI 在 unsubscribe 后仍持有 PC 新建会话写入锁：Desktop 模式在首轮结束后关闭连接器自己的
   空闲 app-server 子进程，并等待其退出；不关闭 Desktop，不影响 ECS 常驻运行方式。

本地验证：303 项主测试、5 项构建后扩展测试和全部 TypeScript 检查通过。

## 后续修正：扩展 CSP 警告

用户反馈 Chrome 扩展错误页出现 `connect-src` 的 `ws://[::1]:*` 无效来源警告。
此前功能验收未检查 CSP 日志；在 Chrome for Testing 151.0.7922.34 打开旧构建的扩展页面，
已通过 DevTools 日志复现同一错误。修正后重新加载构建并检查日志，该警告不再出现。

- 删除 Chrome CSP 不接受的 IPv6 字面来源；保留公网 `wss:` 和本机 `localhost`、`127.0.0.1` 的 WS。
- 地址解析同步拒绝 HTTP IPv6 字面地址并提供明确提示，不将 CSP 放宽为任意 `ws:`。
- 真实浏览器中两个本机 WS 地址均连接成功；304 项主测试、5 项构建后扩展测试及类型检查通过。
- 仅扩展需要重新加载，旧错误记录可清除；本次不重启或重新部署 Relay/Web、PC/ECS 连接器。

用户再次反馈同一警告及 `0.0.1` 显示后，核对本机 Chrome 配置中的扩展目录与更新后的
`extension/dist` 一致，磁盘清单已无该 CSP 项。但原来的固定开发版本无法辨别实际加载的构建。
现改为跟随根项目版本，并以清单与全部构建产物生成内容指纹；Chrome 卡片及弹窗底部均可核对。
在独立 Chrome 中将同一扩展从带旧 CSP 的 `0.0.1` 清单重新加载到新构建，确认实际运行清单、
弹窗版本与磁盘一致，且没有新 CSP 错误。304 项主测试、7 项构建后扩展测试及类型检查通过。
没有操作用户日常 Chrome 的重新加载按钮，因此仍需用户核对当前运行版本，不能仅凭旧错误卡片判断。

## 边界与回滚

日常 Chrome/Edge 配置文件、长时间休眠唤醒、强制 worker 更新、公司代理故障、多个浏览器及
全部 PC 写操作审批组合仍需后续验收。PC 已有 Desktop 会话的审批继续由 Desktop 管理，不能把
ECS 的 Web 审批成功解释成所有 Desktop 审批都能在 Web 处理。

用户现有解压扩展的文件已更新，仍需在 Chrome 扩展管理页点「重新加载」。不会强制关闭日常浏览器。
临时测试配对设备会撤销，测试会话归档；不删除业务会话或覆盖业务消息。

部署前已保存原 Git 提交、Relay 镜像及两端连接器/MCP 配置备份，凭证备份留在私有目录。
回滚应恢复匹配的代码、镜像和配置，并只在空闲窗口重启连接器；不要重建或覆盖现有设备注册表。
